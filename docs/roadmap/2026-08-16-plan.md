# dsh-plugin-wechat 可行方案

> 目标：让 DeepSeek Harness（下文简称 DSH）接入微信，用户通过微信与 DSH agent 对话。
> 遵循 **DSH 插件规范**（Cordis function plugin：`name`/`inject`/`Config`/`apply`），复用 [Tencent/openclaw-weixin](https://github.com/Tencent/openclaw-weixin) 的微信协议层，替换其 OpenClaw 适配层。
> 状态：方案评审稿（待确认 §7 决策项后进入实现）。

---

## 1. 背景与结论

### 1.1 要解决的问题

DSH 目前没有微信（以及任何 IM）接入通道。要让「微信」成为 DSH 的消息入口，正确姿势是**新增一个 DSH 插件**，而不是另起一个外部进程。

### 1.2 复用对象

`openclaw-weixin` 是腾讯官方的 OpenClaw 微信渠道插件（v2.4.6，**MIT 许可**）。它对接的是腾讯 **ilink 微信 bot 网关**（不是企业微信开放 API、也不是公众号 API）：

- 默认后端 `https://ilinkai.weixin.qq.com`，CDN `https://novac2c.cdn.weixin.qq.com/c2c`
- 认证：`AuthorizationType: ilink_bot_token` + `Authorization: Bearer <token>` + `X-WECHAT-UIN`
- 扫码登录（pairing），消息走 `getupdates` 长轮询 / `sendmessage` / `getuploadurl` / `getconfig` / `sendtyping`
- 支持文本 / 图片 / 语音(SILK) / 文件 / 视频，媒体经 CDN + AES-128-ECB 加密

### 1.3 核心结论

- **可行**：openclaw-weixin 的「微信协议层」几乎不依赖 OpenClaw 框架，可整体移植复用；需要替换的只是把它挂到框架上的「适配层」。
- **正确做法（遵循 DSH 插件规范）**：新建一个 DSH Cordis 插件（如 `@deepseek-ai/dsh-im-weixin`），在 `apply()` 里启动微信长轮询，用 `ctx.agents.create()` + `agent.followup()` 把微信消息送入 agent，订阅 session 事件流把回复发回微信。
  - 这才是 DSH 的「一切皆插件」：插件跑在 DSH runtime 进程内，通过 `ctx` 注入的 `agents`/`sessions` 服务驱动 agent，注册与清理都走 `ctx.effect()`。

## 2. 接入形态辨析（为什么上一版推荐是错的）

先厘清三种「接入」的本质区别，避免再混淆：

| 形态 | 是什么 | 遵循 DSH 插件规范？ | 说明 |
|---|---|---|---|
| **DSH Cordis 插件** | 注册进 DSH runtime 的插件，导出 `name`/`inject`/`Config`/`apply`，通过 `ctx` 驱动 agent | ✅ **是** | 本方案采用 |
| 外部 SDK 客户端 | DSH runtime 之外的进程，用 `@deepseek-ai/dsh-sdk-client`（JSON-RPC over stdio）驱动 runtime | ❌ 否 | SDK 客户端不是插件；仅作独立部署/快速原型的备选 |
| 直接复用 OpenClaw 框架 | 用 openclaw-weixin 原样跑在 OpenClaw 上 | ❌ 否 | 放弃 DSH，方向不对 |

> 关键区别：`packages/sdk` 的定位是「从另一进程驱动 Harness runtime」，它是 DSH 的**外部互操作通道**，不是 DSH 的插件扩展点。要让微信成为 DSH 的一部分，应走 Cordis 插件。

## 3. 复用边界

openclaw-weixin 的代码分两层，边界清晰（文件清单来自其 `main` 分支）：

| 层 | 文件 | 依赖 | 处理方式 |
|---|---|---|---|
| **微信协议层** | `src/api/`（HTTP JSON API 客户端 + `types.ts`）、`src/auth/login-qr.ts`、`src/cdn/`（AES-ECB 上传 / 图片解密）、`src/messaging/`（消息编解码、markdown 过滤、context-token 管理、slash 命令）、`src/util/`（logger/random/redact） | 几乎纯 Node | ✅ 移植复用 |
| **OpenClaw 适配层** | `index.ts`、`src/channel.ts`、`src/compat.ts`、`src/auth/accounts.ts`、`src/auth/pairing.ts`、`src/storage/` | 重度 `openclaw/plugin-sdk/*` | ❌ 重写为 DSH 侧适配 |

**替换要点**（OpenClaw 依赖 → DSH/Node 等价物）：

- `resolveStateDir()` / `resolvePreferredOpenClawTmpDir()` → 本项目自有状态目录（`~/.dsh-plugin-wechat/` 或 `Config.stateDir`）。
- `withFileLock()`（infra-runtime）→ Node 自实现 `mkdir`-based 文件锁，或复用成熟依赖。
- `normalizeAccountId` / account 元数据 → 自有账号存储（JSON + 原子写），挂到 `Config.stateDir`。
- `registerChannel` / channel 生命周期 → DSH 插件的 `apply()` 生命周期：`ctx.effect()` 启动轮询，返回 disposer 负责取消与清理。
- `assertHostCompatibility()` → 删除（不再受 OpenClaw 版本约束）。

## 4. 方案详设（Cordis 插件）

### 4.1 总体架构

```
┌───────────────┐  ilink bot HTTP JSON   ┌──────────────────────────────────────────────┐
│ 微信 ilink 网关 │ ◄────────────────────► │  DSH runtime 进程（dsh web / dsh CLI）        │
│ (ilinkai...)   │   getupdates 长轮询     │   └─ 插件 dsh-im-weixin                      │
└───────────────┘                        │      ├─ wechat/  移植的协议层（纯 Node）        │
                                         │      ├─ inbound/ outbound/ 微信↔DSH 适配      │
                                         │      └─ 通过 ctx.agents / ctx.sessions 驱动     │
                                         └──────────────────────────────────────────────┘
```

- 插件与 DSH 同进程，微信长轮询是插件 `apply()` 内的一条 `ctx.effect()` 管理的异步循环。
- 扫码登录是**一次性 CLI 动作**（见 §4.5），登录产物（token）落盘到 `stateDir`，插件运行期只读。

### 4.2 插件骨架（遵循规范）

```ts
// packages/im/im-weixin/src/index.ts
export const name = 'im-weixin'
export const inject = ['agents'] // 用 ctx.agents 创建/驱动 agent；sessions 按需读

  stateDir?: string          // 账号/token 持久化目录，默认 ~/.dsh-plugin-wechat

  provider?: string          // 新会话的 provider/model 路由
  model?: string
  maxTokens?: number
  dmScope?: 'per-peer' | 'per-account-channel-peer' // 会话隔离维度，默认 per-account-channel-peer
  replyErrorAsText?: boolean // agent 失败时给用户回可读错误，默认 true
}

export function apply(ctx: Context, config: Config): void {
  // 1. 读已登录账号（token 来自 §4.5 的 CLI 登录）
  // 2. ctx.effect(() => { startPolling(); return stopPolling }, 'im-weixin: polling')
  //    长轮询循环 + 取消/清理
  // 3. 收消息 → 路由到 agent（§4.3）
}
```

规范要点：`name`/`inject`/`Config`/`apply` 具名导出、**无 default export**；所有注册走 `ctx.effect()`；配置用 schemastery/zod 校验、默认值显式，不写死部署参数。

### 4.3 消息生命周期（核心时序）

以「一条文本消息 → 一条回复」为例：

1. 长轮询 `getupdates` 拿到 `WeixinMessage`（`from_user_id` + `context_token` + `item_list`）。
2. 按 `dmScope` 把 `(accountId, from_user_id)` 映射为稳定 `sessionId`。
3. `ctx.agents.create({ sessionId, agentOptions: { provider, model, maxTokens } })` 得到 `AgentHandle`（首次创建；已存在则 `ctx.agents.get(sessionId)` 复用）。
4. `agent.followup(createUserMessage(text))` 把微信文本作为 next-turn 消息送入 agent 并唤醒 driver。
5. 订阅 `agent.whenIdle()`（或 `ctx.on('session/event')` 读该区间新增的 `assistant/message`），取「这一轮」回复。
6. 经 markdown 过滤后 `sendmessage` 回微信，回传 `context_token`。

**多轮连续性**：微信侧回传 `context_token`；DSH 侧复用同一 `sessionId`（持久化 session 可再配 `sessionPersistence` 实现跨重启 resume）。

**媒体消息**（图片/语音/文件/视频）：
- 入站：CDN 引用（`encrypt_query_param` + `aes_key`）→ `cdn` 下载解密 → 落本地文件 + 文本描述，agent 的 fs/bash 工具可自行处理。
- 出站：`getuploadurl` → AES-128-ECB 加密 → PUT CDN → 组装 `MessageItem` → `sendmessage`。
- 语音：SILK 转码（`src/media/silk-transcode.ts`，依赖 `silk-wasm`）作阶段化能力。

### 4.4 关键设计点

- **同 session 串行化**：DSH 无 per-prompt 结果/cancel 语义，同一 `sessionId` 的微信消息需排队；不同 session 可并发（各自独立 agent）。
- **回复归因**：`agent.followup()` 不返回「对应输出」，与 `agent.whenIdle()` 之间构成一个活动区间；该区间内 session 新增的 `assistant/message` 即为本轮回复（同 SDK `run()` 的 caveat）。
- **生命周期与清理**：轮询循环、in-flight 请求、账号缓存全部由 `ctx.effect()` 返回的 disposer 收敛；插件卸载即停长轮询并取消在途请求。
- **错误与降级**：微信侧 session 超时（`errcode -14`）/token 失效 → 触发告警或要求重新 `login`；agent 侧错误 → 按 `replyErrorAsText` 回一条可读提示。
- **登录与运行分离**：扫码配对是交互动作，放 CLI（`dsh-weixin login`），token 落盘；插件运行期只读，不阻塞 DSH 启动。
- **观测**：复用 `src/util/logger.ts` + `botAgent`（UA 风格，默认 `dsh-plugin-wechat`）用于后端日志归因。

### 4.5 能力 seam 取舍（规范要求）

DSH 规范要求能力 seam 完整（Service Definition / Provider / Consumer）。微信接入有两个演进档位：

- **档位一（最小可行，先做）**：自包含插件，直接在 `apply()` 内驱动 agent，不引入新 seam。快速落地、验证协议。
- **档位二（规范完整，后续抽）**：定义 `ctx.im` Service Definition（inbound 消息投递 + outbound 发送），微信作为 `dsh-im-weixin` Provider，另有一个 Consumer 负责「消息 → agent 路由」。这样未来 Telegram/Discord 等复用同一 seam，各只写 Provider。

推荐按档位一启动，跑通后抽档位二；两者共享同一套移植的协议层。

### 4.6 登录与运行形态

```sh
# 扫码登录（独立 CLI，终端出二维码；token 落盘到 stateDir）
pnpm wechat login
# 在 DSH 的 cordis.yml 里挂载插件，随 dsh web / dsh CLI 一起启动
# - id: im-weixin
#   name: '@deepseek-ai/dsh-im-weixin'
#   config: { provider: deepseek-official, model: deepseek-v4-flash }
pnpm dsh web
```

## 6. 风险与前置条件

1. **ilink 网关权限（前置、阻塞性）**：本通道依赖腾讯 ilink 微信 bot 网关，需能扫码配对拿到合法 token。拿不到则需改企业微信自建应用 / 公众号（另一套协议，复用面缩到「消息编解码思路」）。**须最先确认。**
2. **合规边界**：`ilink_appid: "bot"` + `X-WECHAT-UIN` + 扫码配对属「微信机器人」类接入，存在账号安全/合规边界，需自行评估。
3. **许可证**：openclaw-weixin 的 LICENSE 明确为 **MIT**（GitHub 显示 "Other" 只是未识别其自定义 MIT 声明文本）。移植代码须**保留版权与许可通知**；本项目另选自有许可证。
4. **DSH 预览期无兼容承诺**：插件锁 DSH 版本，随 DSH 升级回归；`sessionId` 语义、`ctx.agents` 接口若有变化需同步。
5. **无 per-prompt 结果/cancel**：继承自 DSH agent 模型（`agent.followup` 只入队、`whenIdle` 才定界），由 §4.4 串行化与归因策略兜底。

## 8. 附：DSH 插件与 agent 驱动接口速查

来源：`packages/core/{agent,agent-loop,session}` 与 `packages/hooks/hooks-claude-code/src/index.ts`（以仓库内 README 为准）。

**插件规范**（function plugin，无 default export）：

```ts
export const name = 'im-weixin'
export const inject = ['agents']
export interface Config { /* schemastery/zod */ }
export function apply(ctx: Context, config: Config): void {
  ctx.effect(() => { /* start */ return () => { /* stop */ } }, 'im-weixin: …')
}
```

**agent 驱动**（经 `ctx.agents`，由 `dsh-agent-loop` 注册 factory）：

```ts
const handle = await ctx.agents.create({
  sessionId,                          // 稳定复用即多轮连续
  agentOptions: { provider, model, maxTokens },
})
const agent = handle.agent
agent.followup(createUserMessage(text)) // 入队 next-turn 并唤醒 driver
await agent.whenIdle()                  // 观察整机 quiescence
// 读 agent.session 的 assistant/message（或 ctx.on('session/event')）取本轮回复
```

**session 事件**：`ctx.sessions`（SessionStore）持有 `Session`；`session.append()` 提交事件，`ctx.on('session/event')` 订阅；`session.deriveMessages()` 投影 LLM 消息历史；`assistant/message` 即模型回复锚点。

要点：`agent.followup()` 只入队、不返回对应输出；`agent.whenIdle()` 与下一次 `followup` 之间构成一个活动区间，该区间内新增的 `assistant/message` 归因为本轮回复（DSH 无 per-prompt 结果）。
